# JC-258 subscription authorization audit

**Status: NOT PROVEN GOOD.** This audit records current behavior and identifies candidate defects and authority decisions. It makes no permission or policy changes. A missing authority rule remains a decision for product and governance owners.

## Scope and evidence

JC-258 asks whether subscription actions enforce the policy matrix, whether customer reads remain owner-scoped, what support can see and initiate, and how public facade functions preserve actor authority. The audit covers the current branch state and labels evidence by what it establishes. It does not certify every handler or every possible facade call path.

The branch is `jc-258-authorization-audit`, based on [JC-257 PR 219](https://github.com/JCSchoeman96/Store_Blueprint_Hardening/pull/219) at `8708e06a7cbb397d4951feeca66acd2c3f426eef`. At JC-258 start, `main` was `12cb5ee4107ca465c9b773b258c1cbae4754b2c7`. The current compiled stack reports 10 resources and 92 actions. Source comparison against that main SHA identifies 90 declared actions; this is not a compiled main runtime certificate. The two stack-only actions are `Subscription.read_access_inventory_window_for_system` and `AccessEffect.read_applied_verification_window_for_system`, introduced by JC-248. This report describes the current stack inventory, not the main inventory.

The [action inventory test](../../test/store/governance/jc258_action_policy_inventory_audit_test.exs) contains the literal map of every action to its current policy group and applicable matrix authority or decision gap. Its guards compare all 92 actions and all 47 facade names against compiled metadata. The table-driven test checks all eight actor contexts for every action with `Ash.can/3`, for 736 policy preflight cells. It preserves `:maybe`, actor-required errors and invalid input separately. No preflight `true` certifies handler execution.

The other modules cover [support setup and detail](../../test/store/governance/jc258_support_payment_setup_audit_test.exs), [direct authorization](../../test/store/governance/jc258_direct_authorization_audit_test.exs), and [stored payment method writes](../../test/store/governance/jc258_stored_method_authorization_audit_test.exs). Their focused results are 6, 7 and 4 passing tests. The inventory module adds six tests. Each implementation task requires specification and quality review. Final exact-head review, repository checks and CI evidence belong in the PR description. The [design](../superpowers/specs/2026-11-07-jc-258-authorization-audit-design.md) records scope and limits.

The inventory test explicitly identifies 13 actions whose synthetic or incomplete preflight input is invalid and checks the observed error-module sets. These cells remain `INDETERMINATE_EXECUTION`. Other valid builders still do not prove the handler's runtime preconditions. The direct tests below supply separate execution evidence for the named operations only.

## Current action inventory and authority

`Store.Subscriptions` registers these ten resources. Counts below are current-stack action counts. The action groups mirror the current resource policies; they are observations, not endorsements. The literal test map linked above supplies the authority label for each action.

The eight contexts are anonymous, owner customer, non-owner customer, support, editor, admin, super-admin and trusted system context. The current preflight groups have these results:

- `public_read` returns true for all eight contexts. `staff_read` returns true for support, admin, super-admin and system.
- `admin_write` and `admin_or_system_write` return true for admin, super-admin and system. `self_or_admin_write` also returns true for the owner customer.
- `system_only` and `system_only_action` return true only for system context.
- `self_read` against the fixture Subscription returns true only for its owner. Other non-nil actors return false; anonymous and system actors lack the user-read action's required actor and produce an input error.
- `owner_or_staff_read` returns true for support, admin, super-admin and system, false for anonymous, and `:maybe` for owner, non-owner and editor. Actual method reads resolve the row visibility as described below.

These are current policy preflight results, not claims that the actions can complete or that every current grant is authorized by the matrix.

The matrix in [policy_matrix.md](../governance/policy_matrix.md#511-subscriptions-subscriptionplan-subscription-renewalattempt) explicitly governs SubscriptionPlan, Subscription and RenewalAttempt permissions. It says SubscriptionPlan reads are active-only for customers, support reads are LIMITED, and admin and super-admin may create/update plans. `archive` and `activate` are update actions covered by that C/U/D row. Subscription reads include the `*_for_system` due-read names where their role is otherwise the matrix R role; a suffix does not itself establish SYSTEM-only permission. Customer self-read and cancellation, admin cancellation, SYSTEM-only Subscription lifecycle actions, RenewalAttempt reads, and SYSTEM-only RenewalAttempt creates/updates have explicit rows.

Several current policy groups conflict with or exceed that authority. Current admin and super-admin allowances on SYSTEM-only Subscription transitions and RenewalAttempt writes are discrepancies. Newer resource grants, the support LIMITED projection, and the `read_for_public` editor allowance are grouped in candidate **JC-369** for an explicit product decision. The matrix says editor NO for SubscriptionPlan reads, while current `read_for_public` allows editor. Do not infer permission from an action name, a neighboring resource row, or the current implementation. JC-369 must reconcile this discrepancy without this audit inventing a new editor rule.

## Direct behavior and facade evidence

The support setup test proves that a support actor can pass the admin Subscription getter and initiate the setup flow. With a local Stripe stub, the call creates and submits a setup PaymentIntent and returns its client secret and publishable key. It also verifies synthetic provider references, and that direct support creation of a PaymentIntent under support actor authority is forbidden. The candidate is the composed facade flow: the getter admits support, then actorless system orchestration performs setup and returns the credential. Track this as [JC-366, support setup initiation and credential exposure](https://linear.app/jc-dev/issue/JC-366/candidate-gate-support-payment-method-setup-before-system-side-effects). The direct PaymentIntent denial does not negate that composed-path result.

The same test reads the actual support detail result. The result contains the Subscription, loaded plan and variant associations, stored payment method, items, five-or-fewer renewal attempts, target lists and action capabilities. The fixture confirms returned values including `user_id`, provider customer and billing references, payment method references and fingerprint. Phase 26 calls `provider_customer_ref` and `provider_billing_ref` optional support snapshots and lists `billing_status_reason` for support visibility ([Phase 26](../phases/phase_26_simple_subscriptions.md)). Those references do not define a complete forbidden-field list or prove that any observed field is prohibited. The matrix's `LIMITED` wording needs an explicit field and surface decision.

The direct authorization test executes valid Subscription `mark_past_due_transition` and RenewalAttempt `mark_processing` actions. Admin and super-admin succeed under current policy, while owner, non-owner, support, editor and anonymous contexts receive forbidden errors; system succeeds. These results establish the current permission mismatch for the concrete actions and fixtures. They do not certify every lifecycle action. Track the SYSTEM-only admin and super-admin discrepancy as [JC-367](https://linear.app/jc-dev/issue/JC-367/candidate-enforce-system-only-subscription-and-renewalattempt-writes).

Direct customer reads and facade behavior establish owner scoping where the action defines it. Owner detail returns its Subscription and nested RenewalAttempt records. The direct Subscription user-read actions filter out a non-owner and return an empty list; a user facade lookup for a non-owner returns `{:ok, nil}`. These are distinct contracts. The Subscription detail helper performs a system-authorized nested RenewalAttempt read after the owner-filtered Subscription getter, so the owner can see the related attempt fields. This is trusted composition in the current facade, but whether every exposed nested field fits customer self-service needs product review. The direct test characterizes this path; it does not grant general RenewalAttempt read permission to customers.

The user plan and variant queue tests prove owner and admin happy paths, and prove that non-owner attempts leave Subscription and ContractChange state unchanged. Support queue attempts return `FORBIDDEN` and leave state unchanged. Cancellation tests prove owner and admin success and support denial. These cases show the tested facade paths preserve actor checks at the relevant mutation. They do not imply coverage of every handler or every possible internal caller.

The support setup denial tests establish that ordinary customer owners, non-owners and editors cannot call the admin setup facade; setup is rejected before provider work. A nil admin actor returns `VALIDATION_ERROR`. For user facades, a non-owner can return `{:ok, nil}`. These outcomes are preserved as action-specific contracts, not normalized into a general denial rule. For nil actors, the inventory test verifies that policy preflight of `read_for_user` and `get_for_user` returns `Ash.Error.Invalid` containing `Ash.Error.Query.ReadActionRequiresActor`. Their query builders are invalid for the same missing-actor contract. These are input errors, distinct from a denied actor. Policy preflight `:maybe`, invalid input, or query filtering must not be reported as an authorization denial.

StoredPaymentMethod direct tests execute `create_or_reuse`, `mark_active`, `mark_inactive`, and `mark_revoked` for anonymous, owner, non-owner, support, editor, admin, super-admin and system contexts. The four writes succeed for admin, super-admin and system and return Ash forbidden errors for the other tested actors. Exact synthetic rows and before/after snapshots establish the write effects. The committed Task 3 test does not cover general row visibility. The inventory test verifies that direct default `read` and `get_for_system` return the exact persisted row for owner, support, admin, super-admin and system; non-owner and editor receive an empty filtered list; anonymous receives `%Ash.Error.Forbidden{}`. Preflight for owner, non-owner and editor remains `:maybe`. No broad cross-handler or cross-user coverage claim follows from these fixtures.

The legacy RenewalAttempt fixtures intentionally leave all nine charged or contract fields nil: `plan_revision_id`, `variant_id`, `quantity`, `amount_minor`, `currency`, `contract_change_id`, `expected_subscription_version`, `charged_contract_version` and `charged_contract_snapshot`. They establish authorization-only transition behavior for a minimal pending attempt. They do not establish financial correctness, concurrency safety, complete renewal execution, or charged snapshot behavior.

The category labels describe intended application consumers in `Store.Support.Governance.SurfaceRegistry`; they are not authenticated roles. Actor-aware USER and ADMIN functions resolve records through actor-scoped getters and pass the actor to the resource mutation where applicable. The audit identified the concrete support setup path above as an exception because its support-readable getter is followed by actorless system setup and credential return. Source inventory is not a complete runtime call-graph proof, and the 33 SYSTEM names do not prove caller confinement by themselves.

## Findings and decisions

- [JC-366](https://linear.app/jc-dev/issue/JC-366/candidate-gate-support-payment-method-setup-before-system-side-effects). Support can initiate payment-method setup through the support-readable admin detail route. The stubbed execution creates and submits a setup intent and returns the client secret. Decide which support roles, if any, may initiate this operation and receive that credential.
- [JC-367](https://linear.app/jc-dev/issue/JC-367/candidate-enforce-system-only-subscription-and-renewalattempt-writes). Current policies allow admin and super-admin on selected Subscription lifecycle and RenewalAttempt write actions that the matrix marks SYSTEM-only. The concrete direct tests prove the current behavior. Align the matrix or policy in a later authorized change; JC-258 itself makes no fix.
- [JC-368](https://linear.app/jc-dev/issue/JC-368/candidate-reconcile-customer-renewal-history-with-direct-read). Owner detail returns its related RenewalAttempt row through system-authorized composition even though direct customer RenewalAttempt read is denied. Decide whether the detail projection may expose those fields to the owner, and define any projection boundary.
- [JC-369](https://linear.app/jc-dev/issue/JC-369/candidate-define-subscription-resource-grants-and-limited-read). Define grants for newer subscription resources and actions omitted from the matrix, including versioned plans, contract changes, variant-plan assignments, stored payment methods, subscription items, collection attempts and access effects. Current policy is evidence of behavior, not authority.
- [JC-369](https://linear.app/jc-dev/issue/JC-369/candidate-define-subscription-resource-grants-and-limited-read). Define what support LIMITED means for Subscription, RenewalAttempt, StoredPaymentMethod and nested detail fields. Phase 26 names `provider_customer_ref` and `provider_billing_ref` as optional support snapshots and lists `billing_status_reason` for support visibility. That guidance does not define a complete projection or a forbidden-field list.
- [JC-369](https://linear.app/jc-dev/issue/JC-369/candidate-define-subscription-resource-grants-and-limited-read). Reconcile `read_for_public` allowing editor with the matrix's explicit editor NO for SubscriptionPlan reads. JC-369 must decide the intended rule; this report adds none.
- [JC-279](https://linear.app/jc-dev/issue/JC-279/newyou-reuse-gap-manual-eft-evidence-human-verification-and-no). The live JC-258 discussion requires separate permissions for manual-payment evidence, matching, verification, rejection, exception classification, correction and proof-of-payment access. Those operations are not implemented and their roles remain undecided. Do not treat absent actions as current permissions or inherit a NewYou policy.

The public facade inventory's SYSTEM methods use trusted internal authority. Their `authorize?: false` composition is not itself a finding. No tenant architecture, tenant identifier, or new role law is proposed.
